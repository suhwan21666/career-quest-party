# 서버 전환 준비 가이드 (v0.11.0)

지금 앱은 **서버 없이** 이 기기(localStorage)에 저장돼요. v0.11.0은 서버를 붙이지 않고, 나중에 붙일 때 데이터를 잃지 않고 검증할 수 있도록 **앱 쪽 준비와 서버 설계 초안**을 만든 버전이에요.

> 상태(2026-11-25): 스키마·보안 정책·동기화 로직을 **실제 PostgreSQL 16**에서 시험했어요(아래 7장). 다만 **진짜 Supabase 프로젝트에는 적용해 보지 않았어요.** Supabase 고유 부분(Auth 토큰 검증, Storage API, Edge Function/Deno 실행, 요금·한도)은 미검증이에요.

## 1. 이번에 앱에 들어간 준비

| 준비 | 내용 | 서버 전환에서 하는 일 |
|---|---|---|
| 기기 식별자 `cid` | 첫 실행 때 임의 값(`c_…`) 생성, 저장에 포함 | 로그인 전 기록을 계정에 한 번 연결(`client_links`) |
| 경험치 이벤트 기록 `S.ev` | 경험치가 오른 모든 순간(퀘스트·습관·달성·보너스 등)을 번호·날짜·종류·근거(기본값 b, 배수 m)와 함께 추가 기록 | 서버가 이벤트로 XP·레벨을 **다시 계산**해서 조작을 막음 |
| 기준선 `evBase` | 이벤트 기록 이전 저장은 그때까지의 총합을 기준선으로 보관, 1500개 초과분도 여기로 합침 | `totalXp = evBase + Σ이벤트` (앱 테스트로 확인) |
| 전송 대기열 `flushEv` | `window.CQ_API.sendEvents` 가 있으면 새 이벤트를 200개씩 전송, 성공(`{ok:true}`)하면 `evSent` 전진, 실패하면 보류 후 재시도 | `CQ_API` 만 꽂으면 동기화 시작. 없으면 아무 일도 안 함 |
| 멱등키 | 이벤트 id = `cid:번호` | 같은 이벤트를 여러 번 보내도 한 번만 저장 |
| 백업 내보내기/가져오기 | 나 → 설정 → "내 기록 백업". JSON(`format:1`)에 기록+사진 | 지금은 기기 변경용, 나중엔 서버 이전용 |
| 가져오기 검증 | 알 수 없는 키 제거, https 외 링크 제거, JPEG data URL 외 사진 제거, 6MB 제한, 확인창 | 서버 업로드 시 같은 검증 재사용 |

### `CQ_API` 계약 (서버 어댑터가 구현할 것)
```js
window.CQ_API = {
  // 이벤트 일괄 전송. 반드시 멱등(같은 id 재전송 무해).
  async sendEvents({cid, build, evBase, events}) {   // events[i] = {id, i, ts, d, k, x, ...근거}
    // → 성공 {ok:true}  (선택: acked = 서버가 받은 마지막 번호)
    // → 실패는 throw 또는 {ok:false}. 앱이 나중에 다시 보냄
  }
};
```
앱은 `build`(앱 버전)와 `evBase`를 함께 보내요. 서버는 `rules.js` 의 `RULES_VERSION` 과 앱 버전을 대조해 규칙 불일치를 감지하세요.

## 2. `server/` 폴더
- `rules.js` — 경험치 규칙 기준 구현. `checkEvent`(기본값·배수·종류·번호·날짜), `replay`(재계산, 하루 종류별 상한), `lvInfo`.
- `replay_test.js` — 앱이 실제로 만든 이벤트(`fixture.json`)를 서버 규칙으로 다시 계산해 앱 총합과 일치하는지, 조작(경험치 부풀리기·배수 초과·번호 역행 등)을 막는지 확인. 실행: `node replay_test.js`
- `gen_fixture.js` — 앱을 실제로 돌려 `fixture.json` 생성.
- `supabase_schema_v2.sql` — 테이블 14개, RLS(본인 행만), `xp_events` 는 서버만 쓰기, 증빙 사진 비공개 버킷, 효과 지표 뷰(`v_user_metrics`, `v_effect_summary`).
- `gen_seed.js` → `seed_habits.sql` — 앱의 습관 104개를 `habits` 테이블 시드로 변환(앱 데이터가 원본).

## 3. 권장 구조 (제안)
Supabase(Auth + Postgres + Storage + Edge Functions). 이유: 이미 v1 온라인 모드가 Supabase 이고 RLS로 개인 데이터를 나누기 쉬움. 다른 선택지도 가능하지만 이 문서의 SQL은 Supabase 기준이에요.
- 로그인: 처음엔 익명 로그인 유지 → 필요 시 이메일/소셜 연결(익명→정식 전환 가능 여부는 **시험 필요**).
- 쓰기 경로: 앱 → Edge Function `sync-events` → `rules.replay` 검증 → `xp_events` 저장(service_role). 클라이언트가 `xp_events` 에 직접 쓰지 못함.
- 사진: 앱에서 900px JPEG를 Storage 비공개 버킷에 업로드, 서명 URL로만 열람.

## 4. 이전 순서 (제안)
1. **서버만 먼저**: 스키마·시드 적용, `sync-events` 구현, 가짜 클라이언트로 `replay_test` 와 같은 케이스 검증.
2. **어댑터 연결**: `CQ_API.sendEvents` 구현(빌드 시 주입 방식은 기존 `CQ_URL/CQ_KEY` 와 동일하게). 기존 사용자는 `evBase` 가 "검증 불가 구간"으로 한 번 올라가고, 그 뒤 이벤트부터 검증돼요.
3. **계정 연결**: 로그인 후 `cid` 를 `client_links` 에 등록(한 번만). 백업 파일 가져오기로도 같은 효과.
4. **상태 동기화**: 습관 진행·한 줄 기록·진단·증빙을 테이블로 업로드(지금은 이벤트만 있음. 이 부분은 아직 앱에 없음).
5. **사진 이전**, **푸시 알림**, **관리자 지표**(뷰 사용) 순으로.

## 5. 개인정보·운영 체크리스트
- 사용자 대상이 청년·구직자라 **만 14세 미만 가입 제한/법정대리인 동의** 여부를 정해야 해요(`profiles.is_minor`, `consent_*` 컬럼만 준비). 법적 판단은 전문가 확인 필요.
- 개인정보 처리방침·동의 화면, 보관 기간, 탈퇴 시 삭제(`on delete cascade` 로 계정 삭제 시 연쇄 삭제, Storage 파일은 별도 삭제 필요).
- 앱의 "개인정보 안내" 문구는 서버 연결 시 **저장 위치가 바뀌므로 반드시 수정**.
- 비용·한도(Supabase 요금제, 스토리지, Edge Function 호출)는 **확인하지 않았어요**. 사용자 수 가정 후 계산 필요.
- 백업 파일에는 글과 사진이 평문으로 들어 있어요. 사용자 안내 문구 포함(앱에 있음).

## 6. 한계·미검증
- 서버 SQL/RLS/Edge 동작: 미검증. 앱과 `rules.js` 만 이 환경에서 테스트함(앱 21항목+서버 규칙 10항목).
- 검증은 "계산이 맞는가" 수준이에요. 사용자가 실제로 습관을 했는지는 서버도 알 수 없어요(증빙도 자기 입력).
- 이벤트 기록 이전의 XP(`evBase`)는 검증할 수 없어요.
- 하루 상한(`LIMITS`)은 앱 동작에서 잡은 넉넉한 값이라 실제 데이터로 조정이 필요해요.
- 파티 기능의 서버 규칙은 스키마만 있고 구현 설계는 아직 없어요.

## 7. 서버 시험 결과 (2026-11-25)
**환경**: 로컬 PostgreSQL 16 + Supabase 흉내 준비(`server/test/supabase_shim.sql`: anon/authenticated/service_role 역할, `auth.uid()`, `storage.objects`). 진짜 Supabase 와 같은 점: 역할 권한·RLS·정책 문법·SQL. 다른 점: JWT 해석(`request.jwt.claim.sub` 설정으로 대체), Storage 서비스 자체, PostgREST, Edge 런타임.

| 시험 | 방법 | 결과 |
|---|---|---|
| 스키마 적용 | `test/run_all.sh` (빈 DB → 준비 → 스키마 → 시드) | 에러 없이 적용, 습관 104행, 정책 14개 |
| 동기화 로직·보안 정책 | `test/db_test.js` | 38항목 통과 |
| 앱 → 어댑터 → HTTP → DB 종단 | `test/e2e_test.js` (실제 앱을 브라우저로 구동) | 7항목 통과: 앱 총합 = 서버 총합, 인증 실패 시 보류 후 자동 재전송, 앱 조작 +400 XP는 서버 총합에 반영 안 됨 |
| 번들 | `build_function.sh` → `core.mjs`, `test/bundle_test.mjs` | Node에서 ESM으로 동작 |

**시험으로 찾아 고친 결함**: `user_total_xp` 함수가 기본으로 모든 사용자(PUBLIC)에게 실행 가능이었음 → `revoke ... from public` 추가.

**확인된 동작**: 사용자는 자기 행만 읽고 씀 / 경험치 이벤트는 사용자가 직접 쓰기·수정·삭제 불가(서버만) / 익명은 아무것도 못 봄 / 지표 뷰는 일반 사용자 접근 불가 / 남의 사진 폴더 쓰기 거부 / 증빙 링크 `javascript:`·긴 메모를 DB가 거부 / 같은 배치 재전송·동시 4건에도 이중 반영 없음 / 남의 기기 ID 가로채기 거부(409) / 하루 상한은 이미 저장된 개수까지 합산 / 깨진 입력에도 서버가 죽지 않음.

**실행**: `server/test/run_all.sh` (로컬 Postgres 필요, 환경변수 `PGMOD` 로 `pg` 모듈 위치 지정), 종단은 `e2e_test.js <앱.html>`.

**Edge Function**: `server/functions/sync-events/index.ts` 는 인증+DB 연결만 하는 얇은 껍질이고 **Deno가 없어 실행하지 못했어요.** 배포 때 가장 먼저 확인할 곳: (1) `SUPABASE_DB_URL` 연결과 `prepare:false` 동작, (2) `auth.getUser` 토큰 검증, (3) `core.mjs` 번들이 Deno에서 로드되는지.

**알려진 한계**
- 인증은 시험에서 가짜(토큰=사용자 id)였어요. 진짜 JWT 검증은 Supabase에서 확인 필요.
- 앱이 1500개 넘게 쌓고 서버에 못 보낸 채 오래 오프라인이면, 접힌 구간은 서버로 가지 못하고 `evBase`로만 남아요.
- 한 사용자가 기기를 여러 개 쓰면 기기별 `cid`·번호가 따로라서 하루 상한은 사용자 기준으로 합산돼요(의도). 정상 사용자가 두 기기로 하루 5퀘스트를 넘기면 거부될 수 있어요 → 실제 데이터로 상한 조정 필요.
- 서버가 막는 건 "계산이 틀린 이벤트"이고, 규칙을 지킨 가짜 활동(매일 퀘스트 5개를 꾸며서 완료)은 막지 못해요.
- 클라이언트 전송 오류(400/409)는 앱이 계속 재시도해요. 영구 오류 구분은 앱 쪽에 아직 없어요.
- 상태 동기화(습관 진행·메모·진단·증빙 업로드)는 아직 서버로 가지 않아요(이벤트만).
